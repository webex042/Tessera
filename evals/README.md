# Evaluations

Synthetic, versioned datasets and the runners that score the **real pipeline code** on them
(plan §18.3). Nothing here contains real user data.

| data | what | size |
|---|---|---|
| `extraction/items/*.json` | screen texts with gold facts, people, due texts; split `dev` / `heldout` | 80 items (22 dev, 58 held-out), 126 gold facts (83 held-out) |
| `ask/ask.json` | questions with gold item ids (retrieval) and answer checks (Stage 6) | 60 questions (8 unanswerable) |
| `draft/draft.json` | draft scenarios (Stage 5) | 20 |
| `../tests/fixtures/injection/cases.json` | prompt-injection corpus, generated by `tools/gen_injection_corpus.py` | 74 cases: 57 tuned + 12 held-out adversarial, 5 genuine controls |

`python evals/validate.py` checks the sets (ids, kinds, every gold evidence and due text is
verbatim in its item).

## Runner: `tsr-eval` (`evals/runner`)

```bash
cargo run -p tsr-evals --bin tsr-eval -- all                      # everything that needs no model (CI)
cargo run -p tsr-evals --bin tsr-eval -- injection                # corpus, SIMULATED compromised model
cargo run -p tsr-evals --bin tsr-eval -- extraction --model oracle --split heldout
cargo run -p tsr-evals --bin tsr-eval -- search
cargo run -p tsr-evals --bin tsr-eval -- backlog
# With real model files (verified against tools/models.lock) on the best local backend:
cargo run -p tsr-evals --bin tsr-eval -- extraction --model D:\models --split heldout
cargo run -p tsr-evals --bin tsr-eval -- injection --model D:\models
```

Each run writes `results/<name>.json` (machine-readable) and `results/<name>.md` (summary).
Exit code 1 = a threshold failed; 2 = the run could not happen (e.g. model files missing).

| runner | measures | simulated parts |
|---|---|---|
| `injection` | per case: no forbidden string stored; only genuine tasks open; no secret in clear; one model call and no other table changed (no action path); content block not closable | the model (unless `--model`) is a worst-case one that obeys every injection |
| `extraction` | precision / recall / F1 (task+commitment grouped, matching rules of `bench/tessara_bench/scoring.py`), hallucinated stored facts, schema-invalid stored rows, needs_review count, rejections by reason | `--model oracle` feeds gold facts back: measures pipeline loss only, never model quality |
| `search` | recall@5/10, precision@5, MRR, nDCG@10 for keyword, vector, RRF, RRF+facts; filter and determinism checks | the vector channel uses the hashing embedder `sim-hash-v1`, not E5 |
| `backlog` | 2-hour workload through the production `SchedulerCore`: completion, drain time after the window, preemptions, queue depth | job costs are assumptions (Stage 0 targets), not measurements |

Definitions used in reports:

- **Hallucinated fact** = a stored fact whose stored evidence quote is not found (normalised
  substring) in its item text, checked independently by the runner. Denominator: stored facts.
- **Schema-invalid row** = a stored fact or evidence row that fails `tsr_pipeline::audit`.
- **Held-out** items and the 12 held-out injection cases are not used to tune prompts or rules.
  The injection held-out set *was* used once to fix the guard after its first run (6/12 passed);
  see `docs/stage2/verification.md`. Fresh cases are needed for an unbiased estimate.

CI (`.github/workflows/ci.yml`) runs `tsr-eval all` on every push; `nightly-evals.yml` runs the
model evaluations on a self-hosted runner when one is configured. Neither downloads models.
